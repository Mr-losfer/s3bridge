# 监控中心与存储体检

监控中心把「服务是否健康、哪里慢、错在哪、空间被谁占了」四件事收敛到一个页面。所有采集都在进程内完成，**不依赖 Prometheus、不引入外部时序数据库**，开箱即用。

设计上有一条硬约束：**采集不能拖慢业务**。因此热路径（每次请求）只做几次原子累加，不做锁、不做 IO、不分配内存。

---

## 1. 性能开销

| 项目 | 实测值 | 说明 |
| --- | --- | --- |
| 单次请求埋点 | **约 148 ns / 0 次内存分配** | `BenchmarkRecord`，串行；并行约 848 ns |
| 概览聚合查询 | 约 15 µs | `BenchmarkSummary`，24 小时窗口 |
| 存储画像（2 万对象） | 约 12.5 ms | `BenchmarkBuildStorageReport`，内存聚合，5 秒缓存 |
| 观测范围 | `/api`、`/s3`、`/mcp` | 静态资源与前端页面不计入，避免噪音干扰 |

接口实测（16 并发压测）：`/api/monitor/summary` P95 约 37 ms、`/api/monitor/storage` P95 约 33 ms，与普通业务接口同量级，没有因为监控而变慢。

## 2. 指标口径

### 2.1 三档时间线与降采样

指标按三个分辨率同时写入，查询时按窗口自动选择精度并降采样，保证任何窗口的返回点数都是可控的（≤ 720 点）。

| 时间线 | 桶宽 × 桶数 | 覆盖范围 | 写入时机 |
| --- | --- | --- | --- |
| `m1` | 60 s × 720 | 最近 12 小时 | 每次请求 |
| `m5` | 300 s × 2016 | 最近 7 天 | 每次请求 |
| `m1h` | 3600 s × 720 | 最近 30 天 | 每次请求 |

查询窗口与返回精度：

| `range` | 数据来源 | 降采样 | 返回步长 |
| --- | --- | --- | --- |
| `1h` | `m1` | 不降采样 | 60 s |
| `6h` | `m1` | 5 桶合并 | 300 s |
| `24h` | `m5` | 3 桶合并 | 900 s |
| `7d` | `m1h` | 3 桶合并 | 3 h |
| `30d` | `m1h` | 12 桶合并 | 12 h |

> 合并时**延迟分位按请求量加权平均**，而不是简单平均。否则一个只有 1 次请求的慢桶会把整体 P95 拉到失真。

### 2.2 计数类指标

| 字段 | 含义 |
| --- | --- |
| `req` | 区间内被观测的请求总数 |
| `ok2` / `ok3` | 2xx / 3xx 响应数 |
| `err4` / `err5` | 4xx / 5xx 响应数 |
| `errRate` | `(err4 + err5) / req`，百分比 |
| `upload` | 路径以 `/api/upload` 开头的请求数 |
| `bytesIn` | 请求体字节数（取 `Content-Length`） |
| `bytesOut` | 实际写出的响应体字节数 |
| `slow` | 耗时 ≥ 800 ms 的请求数 |

### 2.3 延迟分位

延迟用**固定上界直方图**统计，共 15 个桶：

```
1 / 2 / 5 / 10 / 25 / 50 / 100 / 250 / 500 / 1000 / 2500 / 5000 / 10000 / 30000 ms，最后一桶为 +∞
```

P50 / P95 / P99 在命中的桶内做**线性插值**，误差小于一个桶宽（例如 250–500 ms 区间内误差 ≤ 250 ms）。直方图只占固定内存（15 个原子计数），且不会随流量增长。

`avgMs` 不来自直方图，而由精确的 `latSumUs`（微秒累加）除以请求数得到，是真实均值。

## 3. 异常日志

### 3.1 什么请求会进日志

只记录两类，普通成功请求不进日志，避免日志被淹没：

1. **失败**：状态码 ≥ 400；
2. **慢请求**：耗时 ≥ 800 ms（`slowRequest` 常量），即使状态码是 200。

### 3.2 级别与分类

| 级别 | 触发条件 |
| --- | --- |
| `error` | 状态码 ≥ 500 |
| `warn` | 4xx，或慢请求（2xx/3xx） |

分类（`category`）就是后台页面上「什么异常」的筛选维度：

| 分类 | 含义 | 归类依据 |
| --- | --- | --- |
| `auth` | 登录失败、令牌无效、权限不足 | 状态码 401/403，**优先级最高** |
| `s3` | S3 协议错误、签名不匹配 | 路径以 `/s3` 开头 |
| `upload` | 上传失败、文件过大、空文件 | 路径含 `/upload` |
| `plugin` | 插件不可用、调度失败、健康检测失败 | 路径含 `/plugin` |
| `storage` | 对象与桶的 4xx：文件不存在、桶非空、越权删除 | 路径以 `/api/objects`、`/api/buckets` 开头 |
| `system` | 内部错误、panic、更新失败 | 路径含 `/system`、`/settings`、`/user` |
| `request` | 其余通用请求错误 | 兜底 |

> 归类顺序是有意设计的：S3 的 401/403 属于签名问题，先判 `/s3` 归到 `s3`；剩余接口的 401/403 才归到 `auth`。否则「未登录访问任意接口」会被错误地算成业务错误。

### 3.3 单条事件字段

| 字段 | 说明 |
| --- | --- |
| `id` | 事件 ID |
| `time` | UTC 时间 |
| `level` / `category` | 级别与分类 |
| `status` / `method` / `route` | 状态码、方法、**路由模板** |
| `path` | 真实路径（含具体 ID） |
| `actor` / `ip` | 登录用户与来源 IP |
| `latencyMs` | 耗时（毫秒，浮点） |
| `message` | 可读错误消息，从 4xx/5xx 响应体前 1KB 中提取 |
| `fields` | 附加字段：`route`、`query`（≤200 字符）、`ua`（≤120 字符） |

### 3.4 路由归一化

日志按**路由模板**聚合，而不是真实路径，否则 `/api/objects/abc` 与 `/api/objects/def` 会被拆成两行，排行完全失效。

- 路由匹配成功后，后端在响应头写入 `X-Route-Pattern`（如 `/api/objects/{id}`），中间件直接读取；
- 未命中任何路由的请求统一记为 `/api/{unmatched}`，防止扫描器把 404 打成海量独立路由；
- 兜底逻辑会把形似 ID 的路径段替换为 `{id}`。

### 3.5 存储与留存

- 内存环形缓冲保留最近 **5000 条**，查询走内存，毫秒级返回；
- 磁盘按行追加 `{DataDir}/obs/events.jsonl`，单文件超过 **8 MB** 轮转，保留 **3 份**历史；
- 进程重启时只读取文件**尾部 4 MB** 恢复近期事件，启动不会因为日志变大而变慢；
- 查询结果按**事件时间倒序**排序（环形缓冲的写入顺序不等于业务时间顺序，这一点在实现里做了显式排序）。

## 4. 存储体检

### 4.1 检查项

| 检查项 | 说明 | 数据来源 |
| --- | --- | --- |
| 桶容量排行 | 每个桶的对象数、总大小、类型分布、最后上传时间、公开读状态 | 元数据 |
| 类型分布 | 图片/视频/音频/文档/压缩包/其他的对象数与体积 | 元数据 |
| Top 大文件 | 体积最大的 N 个对象（概览 20，深度体检 30） | 元数据 |
| 重复内容 | 相同 SHA-256 的对象分组，统计可回收字节 | 元数据 |
| 断链（missing） | 元数据存在但磁盘文件已丢失 | 逐对象 `stat` |
| 孤儿文件（orphans） | 磁盘有文件但元数据里没有记录 | 遍历对象目录 |
| 超期对象（stale） | 创建时间超过「上传保留天数」设置 | 元数据 + 设置 |
| 即将过期（expiring） | 签名访问地址将在 24 小时内失效 | 元数据 |
| 磁盘占用 | 总量/已用/可用/使用率 | `statfs`（Windows 返回不可用） |

桶的**健康分**：`100 - 断链数 / 桶对象数 × 100`，100 表示该桶元数据与磁盘完全一致。断链是唯一会扣分的项，因为它直接意味着用户下载会 404。

### 4.2 两级体检：快照与深度

| 模式 | 触发 | 耗时 | 覆盖 |
| --- | --- | --- | --- |
| 快照（默认展示） | 打开「存储」页自动加载 | 毫秒级（2 万对象约 12 ms） | 只做内存聚合，**不遍历磁盘**，因此没有孤儿文件 |
| 深度体检 | 点击「开始体检」 | 取决于文件数，2 万对象量级为秒级 | 增加磁盘遍历（孤儿）与逐对象 `stat`（断链），`MaxScanFiles` 上限 20 万 |

深度体检是**异步任务**：

1. `POST /api/monitor/storage/scan` 立即返回 `202`，同一时刻只允许一个任务（重复触发返回 `409`）；
2. 前端轮询 `GET /api/monitor/storage/scan` 获取 `scanning` / `deep` / `scanError` / 起止时间；
3. 任务内做了 **panic 恢复**，单个坏文件不会让整个进程崩溃；
4. 完成后结果写入缓存，前端下一次拉取 `GET /api/monitor/storage` 即拿到 `deep` 报告。

快照结果缓存 **5 秒**，避免前端 20 秒自动刷新时反复做全量聚合；上传、删除等写操作会主动失效缓存。

## 5. HTTP 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/monitor/summary?range=24h` | `system:manage` | 概览：区间汇总、时序、最慢/最易错路由、级别与分类计数、运行时健康 |
| GET | `/api/monitor/events` | `system:manage` | 异常日志，支持 `level` `category` `q` `seconds` `limit` `offset` |
| GET | `/api/monitor/storage` | `system:manage` | 存储画像快照 + 深度体检状态 |
| POST | `/api/monitor/storage/scan` | `system:manage` | 触发深度体检（异步） |
| GET | `/api/monitor/storage/scan` | `system:manage` | 轮询体检进度 |

`/api/monitor/summary` 返回的运行时健康包含：运行时长、goroutine 数、堆内存、系统内存、GC 次数、对象目录磁盘占用。这些是排查「内存泄漏 / goroutine 泄漏 / 磁盘写满」的第一手信号。

## 6. 常见排查路径

| 现象 | 看哪里 | 判断依据 |
| --- | --- | --- |
| 错误率突然升高 | 概览 → 错误率曲线 + 「最易错接口」 | 4xx 多为调用方参数/鉴权问题，5xx 才是服务端问题 |
| 页面变慢 | 概览 → P95/P99 曲线 + 「最慢接口」 | P99 远高于 P50 说明有长尾，通常是上游插件超时 |
| 用户反馈上传失败 | 异常日志筛选 `category=upload` | 关注 `status` 与 `message`，能直接看到上游返回的错误文案 |
| 登录不上 | 异常日志筛选 `category=auth` | 401 集中在 `/api/auth/login` 说明是密码错误，集中在其他接口说明是令牌过期 |
| 磁盘一直涨 | 存储 → 类型分布 + Top 大文件 + 重复内容 | 先看重复内容的 `wastedBytes`，再看孤儿文件 |
| 下载 404 | 存储 → 桶健康分 + 断链列表 | 健康分 < 100 说明有对象的磁盘文件丢了 |
| 图片打不开（本地文件在，但前台显示破图） | 相册筛选「已失效」 | 巡检确认该图片已无法通过 HTTP 返回；详见[图片相册 · 图片有效性](gallery.md#5-图片有效性) |
| 进程变慢且 goroutine 数只增不减 | 概览 → 运行时健康 | goroutine 数持续爬升通常意味着有协程没有退出路径 |

## 7. 相关配置

| 配置 | 默认值 | 位置 |
| --- | --- | --- |
| 指标与事件目录 | `{DataDir}/obs` | `config.ObsDir` |
| 前端自动刷新间隔 | 20 秒 | 监控中心页面 |
| 慢请求阈值 | 800 ms | `internal/api/middleware.go` 常量 `slowRequest` |
| 事件内存保留 | 5000 条 | `internal/obs/events.go` 常量 `eventCapacity` |
| 事件磁盘轮转 | 8 MB × 3 份 | 同上 |
| 指标落盘间隔 | 5 分钟 | `Collector.loop` |
| 快照缓存 | 5 秒 | `storageSummary` |
| 图片有效性巡检间隔 | 72 小时（可改） | 系统设置 `imageValidityIntervalHours` |
| 图片巡检失败阈值 | 2 次 | 系统设置 `imageValidityFailThreshold` |

指标快照以 `gob` 编码写入 `{DataDir}/obs/metrics.gob`（含版本号与校验），因此**重启不会丢失历史曲线**；版本不匹配时自动丢弃，从头开始统计。
