# 全站图片相册

相册页把**所有存储桶里的图片**汇成一面墙，按上传时间倒序排布，支持两种卡片布局切换与灯箱大图。它回答的是「这个站里到底有哪些图」，而不是「某个桶里有什么」。

入口：后台侧栏「图片相册」（需要 `upload:read` 权限）。

---

## 1. 交互

| 能力 | 说明 |
| --- | --- |
| 两种布局 | **网格**（等高裁切，密度高、适合快速扫视）与**瀑布流**（保持原始宽高比，适合看图）；选择记在 `localStorage`，下次进入保持不变 |
| 无限滚动 | 滚动到底部自动加载下一页，不出现「上一页/下一页」按钮 |
| 时间筛选 | `1 天 / 7 天 / 30 天 / 全部` 快捷范围 |
| 桶与关键字 | 按存储桶过滤，按文件名或对象键搜索 |
| 有效性 | 按巡检结果过滤（全部 / 正常 / 已失效）；失效图片左上角有红色角标，灯箱底部显示巡检时间与原因 |
| 灯箱 | 点击放大，左右方向键切换，`Esc` 关闭；大图走**带鉴权的 blob 加载**，不暴露裸链接 |
| 顶部汇总 | 当前筛选条件下的图片总数与总体积，以及各桶图片数量 |

列数随窗口宽度自适应：手机 2 列、平板 3–4 列、桌面最多 6 列。

---

## 2. 流式分页：为什么用游标

相册是无限滚动，如果用 `offset`，翻到第 50 页时后端要「跳过 2400 条再取 48 条」，越翻越慢。

这里改用**游标（cursor）**：每页返回 `nextCursor = base64(创建时间UnixNano|对象ID)`，下一页从该位置继续，定位成本恒定为 `O(limit)`，与翻了多少页无关。

```
GET /api/gallery?limit=48
→ { "items": [...], "nextCursor": "MTczMjc3...", "total": 128, "totalBytes": 93481233, "buckets": [...] }

GET /api/gallery?limit=48&cursor=MTczMjc3...
```

游标用「创建时间 + ID」双字段而不是只用时间，是因为同一批上传可能落在同一时间戳上，只用时间会漏图或重复。

`nextCursor` 为空字符串表示已到末页。

### 请求参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `limit` | 48 | 每页数量，上限 120，超出按 48 处理 |
| `cursor` | — | 上一页返回的 `nextCursor` |
| `bucket` | 全部 | 存储桶名 |
| `q` | — | 关键字，匹配文件名与对象键（不区分大小写） |
| `from` / `to` | — | 时间范围，支持「最近 N 秒」整数或 RFC3339 |

### 权限

- 管理员（`system:manage` 或管理员角色）看到全站图片；
- 普通用户只看到**自己上传**的图片；
- 汇总里的 `total` 与 `buckets` 也遵守同样的可见性，不会泄漏他人数据规模。

## 3. 缩略图

相册一屏可能同时显示几十张图，直接加载原图会打爆带宽与内存。

```
GET /api/objects/thumb?bucket=<桶>&key=<对象键>&w=480
```

| 行为 | 说明 |
| --- | --- |
| 生成 | 标准库 `image.Decode` 解码 → 手写双线性插值缩放 → JPEG 编码 |
| 缓存 | 落盘到 `{DataDir}/thumbs/<width>/<sha前2位>/<sha>.jpg`，二次请求直接命中文件，不再解码 |
| 并发 | 同时最多 2 个生成任务（信号量），批量加载不会打满 CPU |
| 去重 | 同一张图并发请求只生成一次（singleflight） |
| 尺寸 | `w` 默认 480，范围 64–1600 |
| 缓存头 | `Cache-Control: private, max-age=604800, immutable` + `ETag: "<sha256>@<width>"`，支持 `If-None-Match` 返回 304 |
| 超大图 | 源图超过 4000 万像素直接回退原图，避免解码吃掉内存 |
| 不支持格式 | WebP / AVIF 等标准库无法解码的格式（`ErrThumbUnsupported`）**回退到原图 307 重定向**，保证相册永远不出现破图 |

因为缩略图按 `SHA-256 + 宽度` 命名，同一张图被重复上传到不同桶时只占一份缓存；删除对象也不会立刻清理缩略图（属于可接受的缓存残留，清理数据目录即可）。

## 4. 与上传列表的区别

| 页面 | 视角 | 适合场景 |
| --- | --- | --- |
| 上传列表 | **单桶 + 表格**，含插件、状态、大小等运维字段 | 排查某次上传是否成功、看某个桶的内容 |
| 图片相册 | **全站 + 图墙**，只保留看图需要的字段 | 快速巡视站点素材、找某张图、向他人展示 |

两者共用同一份对象元数据与同一套鉴权，不会出现「相册能看到、列表看不到」的不一致。

## 5. 图片有效性

相册不只展示图片，还展示「这张图还能不能打开」。系统按周期巡检本站归档的图片：

- 默认每 **72 小时（3 天）** 检查一次，间隔可在「系统设置 → 图片有效性巡检」调整，也可由插件清单单独覆盖。
- 只发 `HEAD`（上游不支持时退回 `Range: bytes=0-0` 的 GET），只看响应头，**不下载正文**，因此对流量与磁盘几乎无影响。
- 判定 `200/206` 且 `Content-Type` 为 `image/*` 即为正常；连续失败达阈值（默认 2 次）才标记失效并生成告警。
- 判定结果存在对象元数据的 `validity` 字段里：`status`（`ok`/`invalid`/`unknown`）、`checkedAt`、`failCount`、`httpStatus`、`contentType`、`error`。

接口层用 `validity=ok|invalid` 过滤：

```
GET /api/gallery?limit=48&validity=invalid
```

这让「哪些图已经挂了」变成一个可以直接筛选的列表，而不是靠肉眼翻。

## 6. MCP 对应能力

Agent 可以通过 `gallery_list` 工具做同样的巡视：

```json
{"name":"gallery_list","arguments":{"limit":24,"bucket":"","q":""}}
```

返回文件名、桶、对象键、大小、上传者与缩略图地址，便于 Agent 判断「站点里有没有这类图」而无需逐桶遍历。
